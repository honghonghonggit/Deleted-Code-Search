## 게이트 1 측정 방법 (라벨링 전 사전 확정, #37)

### 왜 지금 정하나

라벨링이 시작되기 전에 측정 코드가 커밋되어 있어야 한다. 라벨 결과를 보고 나서 임계값이나 집계 방식을
정하면 "60%가 나오도록 맞춘 것 아니냐"에 방어할 수 없다. 커밋 날짜가 그 증거다.

그래서 판정에 쓰는 숫자는 `eval/gate1.py` 상단 상수 한 곳에만 있고, 각 상수 위에 출처(§)가 주석으로 달려 있다.
`tests/test_gate1.py` 가 그 값(0.5 / 0.8 / 60% / 40% / 0.6)을 고정한다. **바꾸려면** 게이트 회의에서 결정하고,
그 커밋 본문에 결정과 근거를 적는다. 리포트(JSON)에는 측정에 쓴 상수가 함께 기록되므로, 어느 기준으로 잰
숫자인지 나중에도 확인할 수 있다.

### 입력과 실행

라벨러가 채우는 파일은 라벨 가이드 §7.2 개인 라벨(`datasets/labels/{labeler}_pre200.jsonl`)이다.
`tools/label_cli.py` 로 채운다 (README "라벨링").

```bash
python -m eval.gate1 datasets/labels/sj_pre200.jsonl datasets/labels/jh_pre200.jsonl \
    datasets/labels/hs_pre200.jsonl --json-out gate1.json --md-out gate1.md
python -m eval.gate1 datasets/labeled_500.jsonl      # 토론 확정(final)이 들어간 병합 파일
```

- 병합·등급 확정·쌍별 kappa 는 #34 `classify/labels.py` 를 그대로 쓴다. 같은 계산을 두 곳에 두지 않는다
- 8종·3등급 밖의 값, INFERRED 인데 신뢰도 없음, UNK 와 UNKNOWN 불일치, 같은 사람의 같은 레코드 중복이
  있으면 **숫자를 내지 않고 멈춘다** (파일:줄 번호 보고). 틀린 숫자로 게이트를 판정하느니 멈추는 편이 낫다

### 3구간 보고 규칙

**회수율은 단일 숫자로 보고하지 않는다.** INFERRED 를 어디까지 믿느냐에 따라 숫자가 움직이는데,
하나만 내면 그 민감도가 보이지 않는다.

| 구간 | 분자 | 경계 |
|---|---|---|
| ① EXPLICIT만 | EXPLICIT | — |
| ② EXPLICIT + INFERRED(≥ 0.5) | EXPLICIT + 신뢰도 **0.5 이상** INFERRED | 정확히 0.5 는 **포함** |
| ③ EXPLICIT + INFERRED(≥ 0.8) | EXPLICIT + 신뢰도 **0.8 이상** INFERRED | 정확히 0.8 은 **포함** |

- **분모는 세 구간 모두 같다:** 근거 등급이 확정된 레코드 수. 확정 = 토론 확정(`final`)이 있거나 2인의 등급이 일치.
  2인 등급이 갈렸거나 1인만 라벨한 건은 분모에서 빼고 건수를 따로 보고한다 (#34 와 같은 규칙).
  한쪽을 골라 세면 회수율이 토론보다 먼저 정해진다
- **INFERRED 의 신뢰도:** 토론 확정(DISCUSSED·THIRD_PARTY)이면 그 값, 아니면 **2인 중 작은 값** `[팀 확정 필요]`
- 가이드 §6.2 는 0.5 미만 INFERRED 를 금지하므로, 규칙을 지킨 라벨에서 **②가 CHARTER §15 정의 그대로의 회수율**이다.
  0.5 미만 INFERRED 가 있으면 어느 구간에도 세지 않고 경고로 건수를 낸다
- 저장소별 3구간도 함께 낸다 (§10.5, `docs/repo_final20.md` 재평가용). 건수가 적은 저장소는 신뢰구간이 넓다

### 판정 기준 (CHARTER §9 2주차)

| 회수율 | 판정 | 경계 |
|---|---|---|
| ≥ 60% | 진행 | 정확히 60% → **진행** |
| ≥ 40%, < 60% | 저장소 기준 강화 | 정확히 40% → **저장소 기준 강화** |
| < 40% | 대체 코드 중심으로 축 이동 | |

- 각 구간에 위 기준을 따로 적용한다. **세 구간 판정이 모두 같을 때만 그 판정이 확정**이고,
  하나라도 다르면 `판정 갈림 — 회의 필요`를 출력한다. 판정은 게이트 회의(`docs/meetings/gate-1.md`)에서 사람이 정한다
  `[팀 확정 필요]` (CHARTER §9 는 기준을 하나로만 적었다. 구간이 갈릴 때의 처리는 #37 에서 조장이 정한 규칙)
- 비율은 분수로 비교한다. 120/200 같은 값이 부동소수 오차로 경계 아래로 떨어지지 않는다

### 라벨 일치도 (게이트 1 과 함께 보고)

- Cohen's kappa 는 **2인이 모두 라벨한 건만**, 라벨러 쌍별로 따로 (가이드 §8.4). `anchored` 태그 건은 제외
- `reason_label`(8클래스)과 `evidence_grade`(3클래스)를 각각. p_o·p_e·혼동 쌍 상위 3개를 함께 낸다
- **kappa < 0.6 이면 CHARTER §11 라벨 품질 리스크 경고:** 라벨 가이드 개정(§5 보강), 애매 클래스 병합 검토
  (DESIGN/FEAT 등, 병합은 §13 절차). 정확히 0.6 은 경고하지 않는다
- 이유·등급 분포와 이유 × 등급 교차표를 개별 라벨 기준, 확정 레코드 기준으로 각각 낸다

## 게이트 2 사전 등록 (500건 라벨 전 확정, #91)

**확정일: 2026-09-23.** 근거와 대안은 [ADR-016](adr/016-gate2-accuracy-criteria.md).

### 언제 확정했나

**500건 본 라벨 파일이 하나도 없는 상태에서 확정했다.** 2026-09-23 기준 `datasets/labels/` 에 있는 것은
예비 200건(`*_pre200.jsonl`, `gate1_pre200_merged.jsonl`)뿐이고, `docs/reports/` 에도 500건 결과가 없다.
게이트 1의 `eval/gate1.py`(#37)·ADR-012와 같은 순서다. 결과를 보고 기준을 맞췄다는 반론은 커밋 날짜로 막는다.

CHARTER §10.2의 원래 목표는 절대 80%였다. 게이트 1에서 사람 간 `reason_label` 쌍별 단순 일치율이
**40.9~57.6%** 로 측정돼(`meetings/gate-1.md`), 분류기의 정답을 사람이 만드는 이상 절대 80%는
분류기 성능이 아니라 라벨 일치도를 재는 기준이 된다. 그래서 기준을 사람 간 일치율에 묶었다.

### 판정에 쓰는 기준 (둘 다 충족해야 통과)

| # | 기준 | 값 |
|---|---|---|
| ① 정확도 | 테스트 100건 정확도 ≥ **min(80%, H)** | 80%는 상한. 기준이 원래보다 엄격해지지 않는다 |
| ② 기준선 | 우리 방식 정확도 ≥ **max(기준선 A, 기준선 B) + 10%p** | §10.2 그대로, 변경 없음 |

하나라도 미달이면 CHARTER §9 버퍼 규정을 따른다 (확장 축소, 최악의 경우 7주차 산출물로 제출).

### H 정의

**H = 테스트 100건에서 두 라벨러의 독립 라벨 `reason_label` 단순 일치율.**

- **독립 라벨**은 §8.3 토론 확정 **전**의 개별 라벨이다. 분류기 정확도의 정답은 토론 확정 라벨이고, H의 입력은 아니다
- **쌍별이 아니라 테스트 100건 전체를 풀링**한다. 분모는 독립 라벨이 2개인 레코드 수, 분자는 두 값이 같은 레코드 수
- **`anchored` 라벨은 제외한다.** 독립 라벨이 아니다 — `classify/labels.py` `pair_labels()` 와 같은 기준이다.
  **제외해서 분모에서 빠진 건수를 함께 보고한다**
- **계산 시점: 테스트 100건의 토론 확정이 끝난 직후, 분류기를 테스트에 돌리기 전**이다. H 값을 먼저 기록하고 분류기를 돌린다.
  순서가 뒤집히면 분류기 점수를 보고 기준을 정하는 모양이 되어 사전 등록의 의미가 없어진다
- kappa 가 아니라 단순 일치율이다. 우연 일치를 보정하지 않는다 (ADR-016 한계)
- 과거 값(예비 200건 40.9~57.6%)은 **근거로만 쓰고 기준값으로 쓰지 않는다.** 가이드 v2(#40) 후 일치율이 바뀌므로,
  기준은 판정에 쓰는 같은 테스트 100건에서 잰 H로 정의한다

### 평가 절차

- **테스트 100건은 최종 1회만 평가한다.** 기준선 A/B도 같은 100건에서 같은 시점에 잰다
- 개발·튜닝은 **학습 300 / 검증 100**과 **합의 102건**(예비 200건 중 `reason_label` 일치분, 200 − 불일치 98)으로만 한다
- **합의 102건은 테스트 100건에 들어갈 수 없다.** 500건 추출 시 레코드 단위(`commit_sha` + `file_path` + `function_name`)로
  겹침을 배제하고 **제외 건수를 기록한다** (#85). 예비 200건은 `pydantic/pydantic` 1개 저장소이고 500건은 20개 저장소에서
  뽑으므로 같은 레코드가 다시 뽑힐 수 있다. 배제하지 않으면 개발에 쓴 건이 테스트에 섞인다
- **함께 보고하되 판정에 쓰지 않는 것:** 클래스별 F1, 혼동 행렬, 근거 등급별 정확도, `reason_label` kappa
- 판정 스크립트는 **#92**에서 만든다

### LLM 모델 고정 (2026-09-24, #59)

**분류기 학습·평가(#86) 전에 고정했다.** 기준선 B와 우리 방식의 LLM 후보가 같은 설정을 쓴다.
결과를 보고 모델을 고르면 기준선 B를 약하게 만들 여지가 생기므로, 모델은 val·test 결과가 하나도 없을 때
예비 레코드 5건의 **응답 형식**과 속도로만 골랐다 (고른 과정은 PR #137).

| 항목 | 값 |
|---|---|
| 공급자 | NVIDIA API (build.nvidia.com 무료 키, `--provider nvidia`) |
| 모델 | `deepseek-ai/deepseek-v4.1-flash` |
| 생각 과정 | 끔 (`chat_template_kwargs: {"thinking": false}`) |
| `temperature` | 0 |
| `max_tokens` | 256 |
| 프롬프트 버전 | 기준선 B `b1`, 우리 방식 LLM 후보 ~~`c1`~~ → **`c3`** (2026-10-11, #86. 아래) |

- 코드 상수는 `classify/baseline_llm.py` 의 `NVIDIA_MODEL`·`NVIDIA_REQUEST_OPTIONS`·`MAX_ANSWER_TOKENS` 다
- 응답은 `프롬프트 버전 | 모델 | 프롬프트` 로 캐시한다. **#86·#87을 실제로 돌릴 때 그 캐시를 저장소에 커밋한다** -
  무료 카탈로그에서 모델이 빠져도 같은 답으로 다시 채점할 수 있어야 한다
- **test 100건을 돌리기 전에 모델이나 설정을 바꾸면 이 표를 먼저 고친다.** test 를 본 뒤에는 바꾸지 않는다
- 무료 한도나 품질로 Anthropic 유료로 바꾸게 되면(`--provider anthropic`) 같은 방식으로 이 절에 날짜와 함께 남긴다
- **2026-10-11 (#86): 우리 방식 LLM 후보 프롬프트를 `c1` → `c3` 로 바꿨다.** test 를 보기 전이고, 고른 근거는 학습 300건 교차 검증이다
  (`docs/reports/classifier_val.md` §3). 모델·생각 과정·`temperature`·`max_tokens` 와 기준선 B `b1` 은 그대로다.
  c3 는 라벨러 화면(추가 헝크 포함)과 가이드 v3 판정 순서 요약을 준다 - 기준선 B 와의 차이에 맥락뿐 아니라 이 요약도 들어 있다
- 응답 캐시 위치는 `datasets/llm_cache/` 다 (#86). 처음 기본값이 `data/` 아래라 커밋 대상이 아니었다

### 한계 (판정 기록에 함께 적는다)

- **비대칭이다.** 분류기는 토론 확정 라벨과 비교하고, H는 독립 라벨끼리 비교한다.
  "토론 확정 라벨이 두 독립 라벨보다 정답에 가깝다"는 가정이 들어 있고, 이번 데이터로 검증하지 않는다
- H 의 표본은 100건이라 신뢰구간이 넓다. 판정이 경계에 걸리면 그 사실을 적는다

### 판정

- **질문: "배울 게 있는 의미 있는 삭제인가?" 예/아니오.** 3인(sj·jh·hs)이 독립으로 200건 전부 판정한다.
  판정이 끝날 때까지 서로의 파일을 보지 않고, 개별 건을 이야기하지 않는다
- **경계는 라벨 가이드 §6.3.3 그대로다.** 순수 이동·리네임·이동+리네임(유사도 0.9에 조금 못 미쳐도 눈으로 보아
  그러면)·가까운 다른 커밋에서 그대로 재등장 → **아니오**. 같은 자리에서 크게 다시 씀·옮기면서 크게 다시 씀·
  대응 구현이 부모 커밋에 이미 있었음·실제 삭제 → **예**. 그 밖(아주 짧은 부분 삭제 등)은 질문 그대로 판단하고
  `note` 에 이유를 적는다
- **최종 판정은 3인 다수결**이다 (2값이라 동률이 없다)
- 판정자가 보는 것: 저장소, 파일 경로, 함수 이름(시그니처), `deletion_kind`, 삭제된 본문과 줄 수, 커밋 메시지,
  커밋 링크, 그리고 있으면 "참고: 같은 커밋의 비슷한 함수(경로·이름·줄·유사도)". `filter_status`·
  `filter_rule_version`·`filter_evidence` 는 판정용 파일에 없다. 삭제 줄 수는 **모든 건에** 같은 식
  (`len(deleted_body.splitlines())`)으로 보여 준다 — NOISE_TRIVIAL 건에만 보이면 그 자체가 표시가 된다

### 지표와 목표

| 지표 | 정의 | 판정에 쓰나 |
|---|---|---|
| **정밀도** | 통과 표본 100건 중 최종 "예" 비율 | **≥ 90%** (경계 포함) |
| **Fleiss kappa** | 3인 200건, 범주 2개(예/아니오) | **≥ 0.7** (경계 포함). 정의 불가(모두 한 범주)면 미달로 본다 |
| 재현율 | **층별 모집단 크기로 가중**: N_k·p_k / (N_k·p_k + N_move·p_move + N_trivial·p_trivial). N = `recent_only` 거른 뒤 층별 모집단 크기, p = 층별 표본의 최종 "예" 비율 | 보고 |
| **NOISE_MOVE 오판율** | NOISE_MOVE 층 50건 중 최종 "예" 비율 — 이동으로 제외됐는데 배울 게 있다고 본 것. Wilson 95% 구간과 함께 | 보고. #80 보류 항목 재검토의 근거 |
| 쌍별 Cohen kappa | 3쌍, `classify.labels.cohens_kappa` | 보고 |
| 혼동표 | 층(KEPT·NOISE_MOVE·NOISE_TRIVIAL) × 예/아니오 | 보고 |
| 정밀도 Wilson 95% 구간 | — | 보고 |

- **재현율을 표본 비율로 내지 않는다.** 표본은 100/50/50 이지만 모집단은 층마다 크기가 전혀 다르다(NOISE_TRIVIAL
  이 KEPT 의 2배를 넘는다). 표본 비율이나 제외를 한 층으로 묶은 가중은 각 층의 "예"를 잘못 센다
- Fleiss kappa 는 층화 표본 200건 그대로 계산한다 (모집단 가중하지 않는다). 판정자가 같은 200건을 얼마나 같게
  보는지를 재는 값이기 때문이다
- CHARTER §10.1 은 kappa 를 "Cohen's kappa" 로 적었다. 3인 판정이라 하나의 숫자로는 Fleiss 를 쓰고, 쌍별
  Cohen 은 함께 보고한다. **판정에 쓰는 kappa 는 Fleiss 다**
- 통과 = 정밀도와 Fleiss kappa 둘 다 충족

### 미달 시

- 정밀도 미달: #80 에서 보류한 항목(**이동+리네임 유사도 0.9 미만**, **커밋 간 이동**)을 20개 저장소 데이터로
  재검토하고 필터를 고친 뒤(규칙 버전을 올려) 같은 절차로 다시 잰다 (§8.4). 표본은 새 조립 결과에서 같은 시드로 다시 뽑는다
- kappa 미달: 판정 기준이 사람마다 다르게 읽힌 것이다. 불일치 건을 모아 경계 문구를 고치고 다시 판정한다.
  정밀도 숫자는 kappa 가 충족될 때까지 확정하지 않는다

### 알려진 한계 (결과 기록에 함께 적는다)

- **판정자가 필터 결과를 짐작할 수 있다.** 상태 표시는 가렸지만 ① "참고: 비슷한 함수"는 NOISE_MOVE 건에만 있고,
  ② PARTIAL 이면서 4줄 이하인 건은 정의상 모두 NOISE_TRIVIAL 이다. 내용을 가리지 않고는 막을 수 없다
- **비대칭.** 제외된 이동 건은 목적지가 보이지만, 필터가 놓친 이동(통과 건)은 목적지가 보이지 않는다. 판정자가
  커밋 링크로 확인하지 않으면 통과 건을 "예"로 볼 쪽으로 기운다 — 정밀도를 높이는 방향의 편향이다.
  CLI 시작 화면에서 의심스러우면 GitHub 에서 확인하라고 안내한다
- 통과 표본 100건이라 정밀도 95% 구간 폭이 약 ±6%p 다. 판정이 경계(90% 근처)에 걸리면 그 사실을 적는다
- NOISE_MOVE 오판율은 50건이라 구간이 넓다 (오판율 10%면 Wilson 95% 약 4–21%). #80 재검토의 방향을 정하는 근거로
  쓰고, 이동 필터의 정확한 오판율로 인용하지 않는다
- 표본에서 NOISE_MOVE 가 모집단 비율(제외의 약 17%)보다 많이 뽑히므로, 판정자가 "참고: 비슷한 함수"를 보는 건이
  늘어난다. 위 첫째 한계(필터 결과 짐작)가 영향을 주는 건도 그만큼 많다

  갈렸는지로 나눠 기록한다
- 정밀도 미달: 1차 원인 분석과 같은 방식으로 KEPT "아니오" 건을 §6.3.3 번호별로 나눠 기록한다. 1차 분석에서 #80 보류
  항목(이동+리네임 0.9 미만, 커밋 간 이동)으로 고쳐지는 건이 0건이었으므로 그 절차를 다시 등록하지 않는다. 필터를 고치면
  규칙 버전을 올리고 **새 시드로 새 표본**을 뽑아 다시 잰다 (§8.4) — 같은 표본으로 규칙을 고르고 같은 표본으로 재지 않는다

### 알려진 한계 (결과 기록에 함께 적는다)

- **1차와의 차이를 어느 하나 덕으로 돌릴 수 없다.** 판정 기준(§6.3.3 1~5번), 판정 화면(추가 헝크), 필터(v0.8
  NOISE_FORMAT)가 동시에 바뀌었다. 판정자도 1차 판정과 원인 분석(#151)을 겪었고, #90 라벨링으로 같은 기준을 더 익힌 뒤
  판정한다. 표본도 다르다. 정밀도·kappa 가 올라도 "필터가 좋아졌다"나 "기준이 명확해졌다" 중 하나로 설명하지 않는다
- **NOISE_FORMAT 층은 판정자가 필터 결과를 짐작하기 쉽다.** 규칙의 입력(커밋 메시지 첫 줄의 포맷 키워드, 삭제 줄이
  추가 헝크에 다시 나타남)이 판정 화면에 그대로 보인다. 그리고 가이드 2번(기계적 포맷 변환)이 규칙과 거의 같은 것을
  묻는다. 그래서 NOISE_FORMAT 오판율은 낮게 나오기 쉽고, 필터의 독립적인 정확도라기보다 규칙과 판정 기준이 얼마나
  같은지를 잰다
- 1차 한계는 그대로 남는다 — "참고: 비슷한 함수"는 NOISE_MOVE 건에만 있고, PARTIAL 이면서 4줄 이하인 건은 정의상
  NOISE_TRIVIAL 이다. 추가 헝크는 **같은 파일**만 담으므로 다른 파일로 간 이동은 화면만으로 보이지 않는다
  (통과 건 쪽으로 기우는 1차의 비대칭이 줄지만 없어지지는 않는다)
- 제외 층이 작아 구간이 넓다. 34·33건에서 0건이면 Wilson 95% 상한이 약 10%, 3건이면 약 3–23%다. 1차(50건)보다 넓다.
  층 오판율은 방향을 보는 데만 쓴다. 정밀도 구간 폭은 1차와 같다 (90/100 이면 82.6–94.5%)
- 500건을 뺀 모집단이라 #90 라벨 데이터와 같은 레코드로 맞대어 볼 수 없다. 대신 같은 판정자가 같은 건을 두 번 보지 않는다

## 500건 라벨링 v3 사전 등록 (51~100번 라벨링 전 확정, #162)

**확정일: 2026-10-08.** 이 절은 **블록별 51~100번 라벨링을 시작하기 전에 main 에 머지된다.** 51번 이후 라벨과 v3 점검
결과를 보고 아래를 바꾸지 않는다 — 게이트 1(#37)·게이트 2(#91)·필터 정밀도(#89)와 같은 순서이고, 커밋 날짜가 그 증거다.
판정 규칙 자체는 라벨 가이드 v3 (`docs/labeling_guide.md` §6.4, §8.3 v3, §8.4.1.1)에 있다.

> 머지 시점의 예외 1건: jh 가 블록 A 51번 1건을 v3 전에 v2 로 저장했다(2026-10-08 00:35). 가이드 §8.4.2 대로 고치지 않고,
> 그 쌍은 §8.4.2.1 의 `혼재`라 v3 점검·최종 v3 집계에서 빠진다.

### 왜 지금 정하나

중간 점검(가이드 §8.4.1, 블록당 처음 50건)에서 세 블록이 모두 기준(kappa ≥ 0.6) 미달이었다.

| 블록 | 쌍 | 분모 | `reason_label` kappa (`p_o`) | `evidence_grade` kappa (`p_o`) |
|---|---|---:|---|---|
| A | sj + jh | 47 (`anchored` 3 제외) | 0.667 (77%) | 0.385 (64%) |
| B | jh + hs | 50 | 0.488 (62%) | 0.582 (72%) |
| C | hs + sj | 50 | 0.434 (56%) | 0.220 (54%) |

(`python -m classify.labels --interim`, 불일치 분석은 `docs/reports/interim_90_disagreements.md`, PR #161)

가이드 v2 §8.4.1 은 미달 블록마다 "규칙 보강 → 버전 올림 → 재라벨 → 재점검, 두 번째도 미달이면 §11" 을 돌게 되어 있었다.
세 블록이 다 미달인 지금 그 고리를 돌면 (1) 개정할 때마다 기준이 바뀌어 같은 데이터셋 안에 규칙이 여러 벌 생기고,
(2) 5주차(§9) 안에 끝나지 않으며, (3) **"kappa 가 나올 때까지 기준을 고쳤다"** 가 되어 kappa 자체가 무엇을 재는지 흐려진다.
그래서 개정을 한 번(v3)으로 끝내고, 그 뒤의 처리를 라벨을 보기 전에 정한다.

### 정하는 것

| # | 항목 | 값 |
|---|---|---|
| 1 | 가이드 재개정 | **v3 가 마지막이다.** 500건이 끝날 때까지 판정에 영향을 주는 규칙을 고치지 않는다. 오타·링크처럼 판정과 무관한 수정은 `guide_version` 을 그대로 두고 한다 |
| 2 | v3 점검 | 블록별 **51~100번 50건**, 두 라벨이 모두 `v3` 인 쌍만, `anchored` 제외 (가이드 §8.4.1.1 4번). 계산은 가이드 §8.4 그대로(`reason_label`·`evidence_grade` kappa, `p_o`, 혼동 쌍 상위 3개) |
| 3 | v3 점검이 0.6 미만일 때 | **가이드를 고치지 않고 끝까지 진행한다.** 블록 정지·재라벨도 없다 |
| 4 | 2인 라벨이 갈린 건 | **그 블록에 들어가지 않은 제3자가 두 라벨 중 하나를 고른다.** A(sj+jh) → **hs**, B(jh+hs) → **sj**, C(hs+sj) → **jh**. 제3자는 새 라벨을 만들지 않고, 한 라벨을 통째로 고른다. 토론으로 확정하지 않는다. `final.method = THIRD_PARTY` (가이드 §8.3 v3) |
| 5 | kappa 보고 | **수치 그대로** 보고서 한계에 적는다. 블록별 분모와 함께. 미달이면 미달이라고 적는다 |
| 6 | 1~50번 | 일치 81건은 v2 라벨 유지, 갈린 69건은 v3 로 독립 재판정 후 4번. **최종 kappa 집계에서 뺀다** (가이드 §8.4.1.1 6번) |
| 7 | 머지 시점 | 이 절은 51~100번 라벨링 시작 전에 main 에 들어간다 |

- **점검을 51~100번으로 하는 이유.** 갈린 69건은 #161 분석과 회의를 거쳐 다시 보는 건이라 독립이 아니다. 토론·재판정한
  건으로 kappa 를 재면 부풀려진다. 일치한 81건은 일치한 것만 남긴 건이라 섞으면 일치율이 정의상 올라간다
- **§11 대응(가이드 개정, 애매 클래스 병합 검토)은 500건 안에서 하지 않는다.** 가이드 개정은 1번으로 막았고, 클래스 병합은
  §13 절차(분류 체계 변경)라 500건 라벨 전체를 다시 해야 한다. 필요하면 500건이 끝난 뒤 별도 이슈로 연다

### 근거

- **게이트 2 가 판정하는 것은 분류기 정확도다** (ADR-016). kappa 는 CHARTER §10.2 의 "함께 보고하되 통과 판정에는 쓰지 않는다"
  목록에 있다. kappa 미달은 게이트 2 판정을 막지 않는다
- **최종 라벨은 일관된 절차로 확정된다** — 전건 2인 독립 라벨 + 갈린 건은 정해진 제3자의 선택. 정답 라벨의 질은 kappa 를
  올려서가 아니라 모든 건에 같은 절차를 적용해서 보증하고, kappa 는 그 정답이 얼마나 갈렸는지를 숨기지 않는 숫자로 남긴다
- **kappa 가 낮으면 H 도 낮다.** 게이트 2 정확도 기준 min(80%, H) 의 H 는 테스트 100건의 독립 라벨 `reason_label` 일치율이다.
  사람이 갈리는 만큼 분류기에 요구하는 수준도 내려가는 것은 ADR-016 이 의도한 설계다. 그래서 보고서에 H 와 kappa 를 나란히
  적어, 기준이 낮아졌다면 왜 낮아졌는지를 읽는 사람이 보게 한다

### H 와의 관계 (게이트 2 사전 등록의 보충)

- 테스트 100건 중 **34건이 1~50번**이고, 그중 **17건이 재판정 69건**이다. H 의 입력인 "토론 확정 전 독립 라벨"을 이 17건에서는
  **v3 재판정 라벨**로 한다 (가이드 §8.4.1.1 — 제3자 선택 전의 마지막 2인 라벨). 재판정은 #161 을 읽은 뒤라 일치 쪽으로
  기울기 쉽고, 그러면 H 가 올라 기준이 **엄격해지는** 쪽으로 움직인다
- 함께 보고한다(판정에 쓰지 않는다): 51번 이후 테스트 66건만으로 낸 H. 두 값이 크게 다르면 그 사실을 판정 기록에 적는다
- 이 보충은 H 정의(게이트 2 사전 등록 "H 정의")를 바꾸지 않는다. 재판정이 생긴 17건에서 "독립 라벨"이 어느 줄인지를 정한 것이다

### 보고서 한계에 적는 것 (500건 결과 기록에 함께)

1. 1~50번 v2 점검 kappa (위 표)와 미달 판정
2. v3 점검(51~100번) kappa — 분모, `혼재` 쌍 수, 0.6 미만이면 그 사실
3. 최종 kappa — 51번 이후 v3 쌍, 블록별 분모 (최대 A 117 · B 117 · C 116, 가이드 §8.4.1.1 6번)
4. 재판정 69건의 v3 일치율 — 참고치, 독립 아님
5. 제3자 선택 건수 — 블록별, 어느 쪽을 골랐는지 (라벨러별)
6. 일치 81건 중 한쪽 이상이 ③을 첫 근거로 든 23건(테스트 22건) — v3 규칙 2 로는 성립하지 않는 근거로 확정된 정답 (가이드 §10.3)
7. 가이드 §11-19~21 — v3 가 정하지 않고 남긴 것

### 알려진 한계

- **v3 가 kappa 를 올렸는지는 깨끗하게 말할 수 없다.** 1~50번(v2)과 51~100번(v3)은 다른 레코드이고, 라벨러는 그 사이에 #161 을
  읽었다. 차이를 규칙 덕으로도, 학습 덕으로도 돌리지 않는다 (가이드 §8.4.2 "한계"와 같은 이야기다)
- **제3자 선택은 라벨러 1인의 판단이다.** 블록마다 제3자가 한 사람으로 고정되어, 그 사람의 해석이 그 블록 갈린 건의 정답이 된다.
  토론보다 빠르고 절차가 같지만, 블록 간 정답 기준이 제3자에 따라 다를 수 있다. 제3자별 선택 경향(어느 라벨러 쪽을 골랐나)을
  5번으로 보고한다
- **CHARTER §10.2 는 "불일치는 토론으로 확정" 이다.** 이 절의 4번은 그 문구와 다르다. 이 절이 머지되면 CHARTER §10.2 문구를
  같은 방향으로 고친다 (§13 대상 목록에는 없지만 평가 계획 변경이라 ADR-016 처럼 CHARTER 변경 이력에 남긴다)

django 는 리뷰 코멘트 70%(최고)가 그 손실을 일부 메운다.

**교차 비교 — 독립 구현 2개가 같은 순위를 냈다.** 선정 CSV 의 `pr_ratio` 와 맥락 결합의 PR 회수율:

| scikit-learn · pydantic · pandas · requests · fastapi | 1.000 | 100% |

**같은 값은 아니다.** 표본과 분모가 다르다 — 선정 CSV 는 최근 1년에서 저장소당 30건, 여기는 최근

**한계.** 표본이 삭제 커밋이 아니라 최근 커밋이다. #5 가 끝나면 삭제 헝크가 있는 커밋으로 다시 재야

**재측정 (2026-09-12, 코드 리뷰 반영 후).** 리뷰 코멘트 페이지네이션·한도 소진 처리·참조 파싱을
고친 뒤 같은 표본으로 다시 돌렸다. **194건 총계는 그대로다** (PR 79.9% / 이슈 25.8% / 리뷰 25.8%
/ 하나라도 84.0%). 고친 것들이 효과를 내는 조건이 이 표본에 없었기 때문이다 — 표본 모드는

### 2026-09-15 — 저장소 선정 기준 v2 (#56)

**왜 이 절이 필요한가.** 게이트 1은 확정 20개로 이유 회수율을 잰다. 어떤 저장소를 어느 구간으로 채굴하느냐가
그 회수율의 전제다. 그래서 기준을 바꾼 근거를 게이트 1 판정 전에 남긴다.

**배경 — 2026-09-14 사전 탐색(#47, 위 절)에서 본 것.**
- `psf/requests`의 FULL_FUNCTION 레코드는 2011–2013에 1,742건, 2014–2017에 1,009건, 2018–2026에 256건이다. 2011–2017에 몰려 있다.
- 같은 구간 표본 커밋의 PR 연결은 2011–2013 50.0%, 2014–2017 91.1%, 2018–2026 92.3%다.
- PR이 연결된 FULL_FUNCTION 10건을 읽었을 때 이유가 읽힌 비율은 requests 약 30%, httpx(2019년 시작) 약 60%였다.
- 데이터가 많은 구간과 이유가 기록된 구간이 어긋난다. §4.3 ③ PR 문화 기준은 "최근 1년 PR 경유 비율"이라 이 차이를 걸러내지 못한다.
  ADR-006(PR 문화 기준)에 저장소 시작 연도가 빠져 있었다.

**근거의 한계.** 30% / 60%는 저장소당 표본 10건, 판정자 1인의 값이고 위 사전 탐색 절 스스로 "게이트 1 판정에 쓰지 않는다"고 적었다.
기준 v2는 그 관찰을 반영한 **가설**이다. 타당성은 게이트 1의 저장소별 회수율로 다시 확인한다 (`docs/repo_final20.md` §5 ①).

**기준 비교.**

| 항목 | v1 (#1) | v2 (#56) |
|---|---|---|
| 시작 연도 | 보지 않음 | 최초 커밋 날짜 (기본 브랜치의 가장 오래된 커밋) |
| PR 연결 비율 | 최근 1년 커밋 표본 30건 | 연도별 표본 5건씩(병합·봇 제외). 히스토리 전체와 채굴 구간을 따로 |
| 2015년 이전 시작 | 구분 없음 | `recent_only` 플래그. 채굴 구간을 2015년부터로 좁힌다. **제외하지 않는다** |
| 2020년 이후 시작 | 구분 없음 | 거르는 규칙 없음. 후보 유지 |
| 점수 | 0.5 × PR(최근 1년) + 0.3 × 이슈 참조 + 0.2 × 규모(전체 커밋) | 0.5 × PR(채굴 구간) + 0.3 × 이슈 참조(최근 1년, v1과 같음) + 0.2 × 규모(채굴 구간 커밋) |

**설계 판단.**
- **제외가 아니라 플래그.** 2015년 이전 시작 저장소를 제외하면 §4.3 초기 후보 예시인 django·pandas·scikit-learn·celery·requests가 한꺼번에 빠진다
  (결과에서 `recent_only`는 6개). 플래그는 채굴 구간만 좁히고, 되돌리기 쉽다.
- **2020년 이후 시작도 유지.** PR 템플릿이 강제되는 시기라 회수율이 더 높을 가능성이 있다. 필터가 붙은 뒤 별도로 측정한다.
- **연도 층화.** 연도마다 같은 수를 뽑아, 커밋이 몰린 해가 비율을 끌고 가지 않게 했다.
- **v1 점수와 CSV 형식은 그대로 둔다.** `score_v2`와 v2 열은 `--history-per-year`를 줬을 때만 계산·기록한다.

**측정 방법과 한계.**
- 최초 커밋: `GET /repos/{repo}/commits?per_page=1`의 Link 헤더 마지막 페이지(= 총 커밋 수)가 가장 오래된 커밋이다. 그 커밋의 author date를 쓴다.
- 연도별 표본: 그 해 커밋 목록의 **첫 페이지(최신 100개)**에서 병합·봇을 뺀 뒤 5개를 고르게 뽑는다. 커밋이 100개를 넘는 해는 그 해 후반부로 치우친다.
- **"FULL_FUNCTION이 나올 만한 구간"은 근사다.** 삭제 레코드 없이는 어느 커밋에서 FULL_FUNCTION이 나올지 알 수 없어, 연도별 일반 커밋의 PR 연결로 잰다.
  삭제 커밋만의 PR 연결 비율과는 다를 수 있다.
- 표본 수가 작다. 연 5건이라 2023년 이후 시작 저장소는 채굴 구간 표본이 15–20건이다.
- 이슈 참조 비율은 v1의 최근 1년 값을 그대로 쓴다. 연도별로 재지 않았다.
- API가 준 최초 커밋 날짜가 `docs/repo_final20.md` §1의 "생성" 연월보다 늦은 저장소가 8개다. 원인은 확인하지 않았다.
  2015년 경계를 넘나드는 저장소는 없어 `recent_only` 판정에는 영향이 없다 (`docs/repo_final20.md` §7.3).
- GitHub `/commits/{sha}/pulls`가 간헐적으로 HTTP 500을 낸다. 첫 실행에서 20개 중 18개가 이 오류 한 번으로 평가가 끝났다.

  두 번째 실행에서 재시도 40회가 모두 복구됐다.
